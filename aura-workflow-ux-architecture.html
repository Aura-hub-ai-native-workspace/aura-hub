AURA Workflow UX Architecture

How the Workflow Automation vision in docs/AURA_WORKFLOW_AUTOMATION_RESEARCH.html becomes an interface — one that makes powerful automation understandable without hiding what the AI is doing.

read-only analysis no source changes no components created nothing committed
The thesis in one paragraph

Every competitor in this space sells the graph. AURA's graph is table stakes — the real product is that a person can watch an intelligent system act on their machine and understand, at every moment, what it intends, what it is permitted to do, what it observed, and why it decided what it did. The interface's job is therefore not to simplify the automation. It is to make the automation legible at four zoom levels: the library, the graph, the run, and the reasoning step. Anything that hides a decision to look calmer is a bug.

Properties that are load-bearing

  • Navigation is store state, not URL. useAppStore.nav ∈ home | workflows | workspace | environment | settings, plus activeProjectId and projectTab. Any new workflow surface is a state, not a route.
  • Route switches never gate on an exit animation. ScreenRouter keys a single motion.div; nesting a second AnimatePresence mode="wait" above a screen that has its own has already caused a permanently blank workspace. This constrains any tabbed workflow shell.
  • The RightPanel is suppressed by screens that supply their own inspector (Code workspace, Workspace screen). The workflow editor already follows the same logic implicitly by owning its own inspector column.
  • Three canvas traditions already exist and mean different things. Author-time DAG (screens/workflows/WorkflowEditor), run-time DAG with deterministic Sugiyama-lite layout (screens/missions/WorkflowCanvas), and non-wireable hub-and-spoke (workspace/HubCanvas — explicitly "not a workflow builder"). Adding a fourth would be a mistake.

The token layer

Two complete palettes keyed off :root[data-theme]. Semantic, not literal: --canvas, --surface, --surface-hover, --surface-active, --line, --line-strong, --text, --text-muted, --text-subtle, --accent (#3b6bff light / #5c86ff dark), and exactly three status hues — --positive, --attention, --danger. Inter at 13px base with cv02/03/04/11; radii cluster at 10–16px; shadows are barely there.

Node families carry their own categorical hues in screens/workflows/shared.ts — source blue, intelligence violet, generate green, logic amber, action rose, io cyan — deliberately separate from the three status hues so state and identity never compete for meaning. This separation is the single most valuable thing in the existing system and every proposal below preserves it.

Motion vocabulary

Three springs (snappy, smooth, fluid) plus four ambient classes already written for exactly this domain: .aura-breathe (a status dot that breathes), .aura-live (a solid dot with a slow expanding halo), .aura-drift, and .edge-flow — "dependency edges stream forward along the path while execution runs". All respect prefers-reduced-motion. The language for live execution is already authored; the workflow work should spend it, not reinvent it.

A structural problem worth naming early

The editor currently reserves 796px of permanent chrome — a 216px palette, a 280px inspector, and a 300px AI Builder panel that is docked permanently and never collapses. On a 1440px window with the 76px nav rail, the canvas gets under 570px. Every feature this report proposes wants panel space, and there is none left. Section H treats panel budget as a first-class design constraint rather than an afterthought.

Research decisions that are really UX decisions

Research findingWhat it demands of the interface
Pattern D — bounded agent: max iterations, timeout, tool allowlist, token budget, structured outputThese five bounds are not settings. They are the agent UI. Design them as a legible contract with a worst-case estimate, not a form.
Prompt injection: "tool outputs as untrusted data"Untrusted data must look untrusted wherever it is shown. Never render tool output as markdown in a trace. Quarantine styling is a security control, not decoration.
Agent's tools ≤ workflow's permissionsMake it structural: tools outside the workflow's envelope are visibly unselectable with a stated reason, not merely rejected at run time.
Capability Fabric is the single governed pathOne permission vocabulary across canvas, inspector, trace and approval. If two surfaces name the same risk differently, the model has leaked.
Approval fatigue → rubber-stampingThe cost of an approval is attention. Batch, tier and scope them; make the rare approval feel rare. A UI that asks twenty times has already failed.
AI-generated workflows must never activate silentlyGeneration ends in a review state, never a live state. Show the graph, explain each node, highlight high-risk actions, require explicit activation.
Lightweight JSON checkpointing"Resume" is a UI promise before it is a storage decision. The run header must say honestly where a run can be resumed from — and when it cannot.
Offline-first is a genuine differentiatorEvery node declares whether it needs network. Show it on the node face. An offline-capable workflow should be visibly, provably offline-capable.
AI provider latency dominates (100ms–2s per call)A duration bar chart tells the truth a spinner hides. Make time-in-node visible so users optimise the right node.
Trust score: tested · no policy violations · dry run passed · within budgetA four-part readiness indicator on the library card and above the Run button. Earned, not asserted.
"Don't clone n8n"The differentiator is that AURA understands the project. Intelligence nodes should be the first thing in the palette and should show live grounding (index freshness, source counts) — not sit in a generic list alongside HTTP.
Where the research is silent and the UX cannot be

The research treats non-determinism as a testing problem. It is also a trust problem, and trust is an interface concern. Two identical runs of the same agent workflow will differ, and users will read that as a bug unless the interface has already taught them otherwise. The proposal: run cards carry a deterministic or reasoned mark, and any run containing an agent node shows a divergence affordance — "this run differs from the last; see where" — turning surprise into an inspectable fact.

The non-duplication rule, from CLAUDE.md

"There is exactly one policy engine, one execution path, one process primitive, one environment scanner, one node catalogue, one DAG builder and one approval store." The UX corollary: there is one timeline component, one approval component, one risk vocabulary and one node card. Mission Control's MissionTimeline and ApprovalGate are the incumbents. Workflow execution extends them; it does not fork them. If a workflow run and a mission render the same event differently, the model has already diverged.

Three standing surfaces under Automation

Today nav: workflows resolves to a library-or-editor binary. It should resolve to a domain with three peers, because the product has three questions and today answers only one:

1 Automations

"What can run?" — the unified catalogue of workflows, rules and schedules. Today only workflows appear here; the Automation Engine's eight trigger types are invisible. One catalogue, three kinds, filterable — not three separate screens.

2 Runs

"What happened?" — every execution, live and historical, across every automation. The single largest missing surface. This is also where resume, retry, replay and run-diff live.

3 Approvals

"What needs me?" — the cross-cutting inbox of pending authorizations from workflows, missions and the agent, batched and risk-tiered. Reachable from the StatusBar and the CommandBar bell, not only from inside a run.

These are tabs within the Automation screen, not new nav keys. The left rail stays at five destinations — it is one of the calmest things about the product and adding to it costs more than it buys.

Four zoom levels — the report's organising idea

L1CatalogueAutomations + Runs + Approvals. Fleet health. What exists and what needs me.
L2GraphOne workflow's structure and state. Nodes, edges, live rings.
L3RunOne execution over time. Timeline, ledger, artifacts, approvals.
L4ReasoningOne agent step's internal argument. The trace.

Every navigation in the system is a move between adjacent levels, and every level is reachable from its neighbour in one click. A user must never have to leave a run to understand a step, or leave a step to understand a decision. The failure mode this prevents is the one every agent product has: a spinner at L2 and a wall of JSON at L4, with nothing in between.

Five interaction rules

1
The graph is never modal. Approvals, traces and inspectors are drawers and inline blocks, never dialogs over the canvas. A person deciding on a git.commit must be able to see the graph that led there. The only justified modal is pre-run input collection, which already works this way.
2
State changes animate; layout does not jump. A node entering running gains its ring over ~150ms and its edge starts streaming with the existing .edge-flow. Nodes never move on their own — auto-layout is always an explicit command, because a graph that rearranges itself during a run destroys the user's spatial memory precisely when they need it.
3
Every wait states its cause and its exit. "Running…" is insufficient. waiting on you · git.commit, waiting on network · retry 2/3 in 8s, waiting on model · 4.2s. A wait with no stated cause is a bug report waiting to be filed.
4
Destructive and irreversible are different words. Delete-a-node is undoable and needs no confirmation. resource.destroy is not, and needs a typed confirmation and an audit record. The interface must never spend a user's caution on the reversible thing.
5
Cancel is always one gesture away. From the canvas, the run header, the trace, the Runs table, the StatusBar. Cancellation is the user's ultimate authority over an autonomous system and must never be more than one click deep.

GAgentic AI Node UX

The one node whose behaviour is not knowable at author time. Everything else in this report is scaffolding for getting this right.

The design problem, stated precisely

Every other node is a function: configuration in, typed output out, behaviour fully determined by its config. The agent node is a contract: you specify a boundary, and something inside it reasons. This means the author-time UI cannot be a settings form — a form implies you are describing behaviour, and you are not. And the run-time UI cannot be a status ring — a ring implies there is one thing happening, and there are ten.

So the agent node needs two interfaces that no other node needs: a contract, and a ledger.

The nine beats

The user's brief names the sequence the interface must communicate. It is a real sequence — each beat causes the next — so it earns structural treatment. Every beat below is a typed row in the trace, coloured by kind, and carries an actor: AI reasons, gates pause, you decide.

01IntentThe task as given, plus the context manifest actually sent.
02PlanThe stated approach for this iteration, before any tool runs.
03ProposalA named capability with concrete arguments.
04PermissionThe Fabric's decision and the rule behind it. Always shown.
05ExecutionRan via the Fabric. Duration, surface, audit id.
06ObservationWhat came back — quarantined as untrusted data.
07DecisionA claim, with links to the observations supporting it.
08InterventionApprove, decline, redirect, or stop — inline, in context.
09ResultTyped output, schema-validated, or a stated reason for stopping.

What each element buys

  • Indigo family hue #6366f1 — adjacent to intelligence violet (it reasons) but distinct from it (it acts). New family, same categorical system.
  • The contract strip — iterations, wall clock, token budget. Legible at a glance, at any zoom above 0.6×. A user scanning a graph can see instantly which agents are cheap and which are expensive.
  • The tool chip is a button, not a label. It opens the permission envelope. This is the single most important affordance on the card.
  • Three output ports, not one. An agent legitimately terminates three ways, and needs-human is a first-class outcome — not a failure.

During a run the card grows exactly two things: a one-line beat ticker (observing · read src/server.ts) that replaces the config preview, and a 2px iteration rail along the bottom edge showing 4/10. Reasoning text never appears on the canvas — at 208px wide it can only be a teaser, and a teaser of an argument is worse than no argument.

Eight rules that make the trace trustworthy

1
Rows are typed by kind, not by speaker. AURA already owns this vocabulary — MissionTimeline's TYPE_META and its AI / You / System actor badges. Reuse it. A second timeline vocabulary is a second source of truth about what happened.
2
Observations are quarantined, always. Tool output never renders as markdown. Monospace, dimmed, left-ruled, byte count, untrusted chip, collapsed past six lines, with a stated provenance line on expand. This is not styling — it is the visual implementation of the research's prompt-injection defence. If the interface never treats tool output as instructions, neither does the reader. A page that renders a fetched web page's markdown into a trusted-looking card has taught the user the exact wrong lesson.
3
Permission rows appear even when auto-executed. Silent auto-execution is where trust dies quietly. One line — ✓ auto-execute · low · project.read — buys complete legibility. Collapse them in aggregate ("18 auto-executed calls, expand") once a run is long, but never omit them, and never collapse a row above low.
4
Decisions carry evidence. Each decision links to the observation rows it rests on; clicking scrolls and highlights them. A decision with no linked observation gets a quiet unsupported mark. This is the difference between a transcript and an argument, and it is the single highest-leverage thing this interface can do for a user's judgement.
5
The budget meters are the header, and they deplete. Three rails plus accumulating cost. At 80% of any limit the header shifts to attention tone. When an agent stops, the terminal row must name which limit stopped it — "reached the 10-iteration cap with no final answer" is a usable fact; "agent failed" is not.
6
Interventions are inline, never modal. The ApprovalGate component renders as a row in the trace, exactly where the reasoning that produced it sits. A modal divorces the decision from its context, which is precisely the social-engineering surface the research's threat matrix names. The canvas node simultaneously enters waiting — the existing attention ring — so the state is visible from L2 as well.
7
No confidence scores. Show what is measured — iterations, tokens, milliseconds, tool calls, evidence count. Never show a percentage the model asserted about itself. A fabricated 94% is worse than no number, because it converts an unknown into a false known.
8
Replay is the same component, frozen. A historical trace renders identically to a live one, minus the meters' motion and with intervention rows showing the decision that was taken and by whom. One viewer, two states — never a separate "history" renderer that drifts.

Two open design calls inside the agent node

call 1 Streaming reasoning: show or withhold?

Streaming the model's tokens live makes the node feel alive and is what every chat product does. It also encourages reading unfiltered model output as fact, and produces text that is frequently revised a second later. Recommendation: stream a one-line beat ("planning", "reading src/server.ts"), and commit the full plan/decision text only when the iteration settles. Liveness without inviting the user to trust a draft.

call 2 Can a user redirect mid-run?

A "steer" affordance — injecting a human note into the agent's context at an intervention — is powerful and is the natural next request after approvals ship. It is also a prompt-injection surface with the user as the injector, and it makes runs unreproducible. Recommendation: ship declines with a reason first (already in ApprovalGate — the reason goes to the audit trail and can equally go to the agent), and treat free-form steering as a later, explicitly-marked capability that stamps the run as steered.

HWorkflow editor UX

The canvas is good. The chrome around it is the problem.

The panel budget, treated as a design constraint

Today: 76px nav rail + 216px palette + 280px inspector + 300px permanently-docked AI Builder = 872px of chrome, leaving under 570px of canvas on a 1440px window. Every feature in this report wants panel space. The rebalance:

PanelTodayProposedWhy
Palette216px, always open, no search240px, collapsible to a 48px icon rail, search-firstAt 40+ node types scanning six category lists is slower than typing. Collapsed by default once a graph exists.
Inspector280px, always open320px, opens on selection, closes on EscMatches the shell's own RightPanel width and its show-on-context behaviour. Empty-canvas state moves to an overlay card, not a permanent column.
AI Builder300px, permanent, never collapsesA command surface — invoked from the toolbar or ⌘K, appears as an overlay composer at the canvas's bottom edgeIt is used for seconds and occupies 300px permanently. Making it summonable returns 21% of the window and matches how ⌘K already works everywhere else in AURA.
Validation strip—28px above the canvas, only when there is something to sayErrors currently surface as a red ring at run time. A strip that says "2 problems · 1 unreachable node" turns run-time surprise into author-time information.
Run drawer260px bottom, Output / LogsBecomes the Runs view (§I); the drawer keeps a compact live summary onlyA 260px drawer is the wrong container for a timeline, a ledger and artifacts.

Net: ~570px of canvas becomes ~1000px in the common case, and the AI Builder gains rather than loses prominence by being a command instead of a column.

Data mapping — the highest-value missing feature

The research calls data mapping "critical UX", and the current model is an opaque NodeIO with untyped {{VAR}} interpolation. The proposal keeps interpolation (it is simple and it works) and makes it visible:

  • Reference chips. Typing {{ in any text field opens an autocomplete of everything actually in scope, grouped by producing node. Inserted references render as chips carrying their source node's family hue — a green chip is generated text, a blue chip came from a project source. Provenance becomes a colour you already know how to read.
  • Edge peek. Hovering an edge after a run shows what flowed: first 200 characters, byte count, file count, type. The single fastest way to answer "why did this node get the wrong input".
  • Unresolved references are validation errors, shown in the strip at author time, not silently interpolated to an empty string at run time.

Validation, in three tiers

blocking

Cycles outside a loop node · a required field left empty · an unresolved {{ref}} · a node whose capability is denied by policy. Run is disabled, with the count on the button.

warning

Unreachable nodes · an output port wired nowhere · a high-risk action with no error route · a network node in an otherwise offline workflow. Run proceeds; the strip stays.

advisory

A stale knowledge index · an agent with an unusually large token budget · a workflow that has never been simulated. Shown in the strip's expanded view only.

Versioning, in the toolbar

The header gains a version chip beside the name: v7 · draft. Saving creates a draft; running promotes the draft to a version, because an executed graph must be immutable if runs are to mean anything. The chip opens the Versions view. Restoring an old version creates a new one rather than rewinding — history is append-only, matching how the Fabric's audit trail already behaves.

The versioning trap to avoid

Auto-versioning every save produces 200 meaningless versions and a useless history. Auto-versioning only on run produces a history where every version was actually executed — which is the history people want ("what changed between the run that worked and the one that didn't"). Manual "save a version" as an escape hatch, with a note field. This is a product decision (§P) but the recommendation is firm.

Scale affordances, in priority order

  1. Palette search — the cheapest win in the entire editor.
  2. Auto-layout — reuse missions/WorkflowCanvas's existing Sugiyama-lite layout rather than writing a second one. Explicit command, never automatic.
  3. Minimap — bottom-right, above the existing zoom controls, showing node state colours so a run's progress is legible while zoomed in.
  4. Subworkflows — ⌘G collapses a selection into one node with declared inputs and outputs. The correct answer to "large workflows become hard to manage"; more valuable than any layout algorithm.
  5. Node search & focus — ⌘F on the canvas, jump to a node by name.

IExecution and debugging UX

One run, three synchronized projections — and the recovery affordances that make a failure survivable.

Three projections of one truth

Graph · where

The canvas at the playhead's moment. Status rings, streaming edges. Answers "where in the structure did this happen?"

Timeline · when

Wall-clock swimlanes, one row per step. Answers "what took the time?" — which for AI workflows is almost always the question.

Ledger · what

Typed events, newest last. Approvals, decisions, observations, artifacts. Answers "what actually occurred?"

Selection is shared. Click a node in the graph → the timeline scrolls to its bar and the ledger filters to its events. Click a ledger row → the graph highlights its node. Drag the timeline playhead → the graph renders the state at that instant. This is what turns three panels into one instrument.

The timeline, specifically

Not a Gantt chart borrowed from a project tool. A wall-clock swimlane tuned to the two things that actually vary in an AI workflow — where the time went and what the system was waiting for:

  • Rows = steps in topological order, so the visual shape mirrors the graph.
  • Bar fill = the node's family hue; bar border = state. Identity and status stay separable, as they are everywhere else in AURA.
  • Waiting is drawn, not hidden. Waiting-on-human renders as an amber hatched band; waiting-on-network as a grey hatched band; waiting-on-model as a solid dimmed band. The research's finding that "AI provider latency dominates" becomes a thing you can see and optimise, rather than a fact in a document.
  • LLM steps carry a token sub-bar under the duration bar, so cost and time are legible in the same glance.
  • The critical path is emphasised; everything else recedes. Reuse the existing convention from missions/WorkflowCanvas.

The cheapest large improvement to this product's UX is writing runs to disk.

Retry, resume, cancel

Retry

Automatic retries are shown while they happen: the node holds retry 2/3 · next in 8s with a countdown, not a frozen spinner. Manual retry of one step is a row action. Retrying a step with side effects warns about idempotency — the research's at-least-once model made visible.

Resume

The run header states resumability honestly at all times: resumable from step 4 or not resumable — no checkpoint. On app restart, interrupted runs surface in Runs with a Resume action. If the definition changed since the checkpoint, resume warns before proceeding, per the research.

Cancel

One click from five places. Cancelling mid-action states what will and will not be rolled back — "the commit already happened and will not be undone." A cancelled run is cancelled, never failed: today stopRun() conflates them, which teaches users that their own deliberate action is an error.

JHuman approval UX

The component is already right. The work is placement, batching, and defending the user's attention.

Keep the five facts

ApprovalGate already requires all five: which capability, against what target, at what risk, why it is being asked, and what happens either way — plus the policy rule that opened the gate, an irreversibility flag, and decline-with-reason recorded to the audit trail. No redesign is warranted. The work is making it appear in three places instead of one:

  1. Inline in the run, at the ledger position where it was raised (§G).
  2. In the Approvals inbox, with a link back to that position.
  3. As a notification, through the existing bell and StatusBar, when the user is elsewhere in the app.

Defending attention — the anti-fatigue design

1
Batch by moment. The Fabric already collapses simultaneous approvals into one request. The UI must render that as one card with an itemised list and a single decision — not n stacked cards, which is functionally the same as n interruptions.
2
Tier by risk, visibly. The inbox groups irreversible above high above medium. A user who has ten pending approvals must be able to find the one that matters in under a second.
3
Standing grants are scoped and expiring, never permanent. Offer "auto-approve filesystem.read for this workflow for 24 hours" — three bounded dimensions. Never offer a bare "always allow". Standing grants are listed in the Permissions view and revocable in one click; the run ledger shows auto-approved by standing grant · expires in 6h so the authority is never invisible.
4
Timeouts pause; they never auto-approve. If nobody answers, the run parks in waiting and stays resumable. Silence is not consent, and a timeout that grants authority is the worst possible default in a system with a shell node.
5
Make the rare approval feel rare. If a workflow raises the same gate on every run, the interface should say so and offer the scoped standing grant — turning a recurring interruption into one deliberate decision. A gate that fires every time has stopped being a decision and become a speed bump.

KSecurity and permission UX

The Capability Fabric is AURA's genuine differentiator. Right now a user cannot see it. That is the whole gap.

The Permission Envelope

One concept, computed from a workflow's nodes, rendered identically wherever authority needs to be legible: the library card, the Permissions view, the pre-activation review, and the agent's tool block.

Permission envelope · Nightly issue triage
PROJECT.READ
auto 4 nodes · reads files and git status in aura-hub
PROJECT.WRITE
asks you 1 node · writes to docs/
PROCESS.EXECUTE
approval 1 node · git.commit — irreversible
NETWORK.OUTBOUND
asks you 1 node · api.github.com only
RESOURCE.DESTROY
not requested
SYSTEM.MODIFY
not requested
This workflow cannot install software, delete resources, or reach any host other than api.github.com.

The closing sentence is the most important element in the whole card. A list of granted scopes tells a user what can happen; a plain statement of what cannot is what actually lets them relax. Absence of authority is information, and it is the information every permission UI in the industry omits.

Where the envelope must appear

MomentTreatmentWhy here
Library cardA single-line summary: 2 high-risk or read-onlyScannable authority across the catalogue
Before the first runFull envelope, requires acknowledgementThe moment authority is actually conferred
After importing JSONFull envelope, blocking — the workflow cannot run until reviewedThe research's supply-chain threat. An imported workflow is untrusted code with a friendly name.
After AI generationFull envelope inside the review state"The AI must never silently create an unsafe workflow"
When the envelope growsA diff: "this version adds process.execute"Privilege creep across versions is invisible otherwise
Agent tool blockThe envelope as the selectable set; anything outside it is struck through with a reasonMakes "agent ≤ workflow" structural rather than advisory

Four security-UX rules

1
Secrets are names, never values. Fields reference {{secret:GITHUB_TOKEN}}; the value lives in the OS keychain and is injected by the Fabric at execution. The UI shows the name, the store, and when it was last used. Where a value could appear in a log or output, the interface renders •••• redacted with a visible mark — a user must be able to see that redaction happened, or they cannot trust that it happens.
2
Untrusted data is marked everywhere it travels. Not just in the agent trace. Web page content, HTTP responses and file contents carry a provenance mark wherever they are rendered — ledger, edge peek, node output, artifact preview. One visual language for "this came from outside and is data, not instruction".
3
Denials explain and offer the next step. The policy engine's four decisions each need a distinct treatment, and deny is the one that must never be a dead end: "Denied — this workflow has no network.outbound scope. Grant it in Permissions, or remove the HTTP node." A denial with no route forward trains users to route around the system.
4
The trust score is earned and decays. Four marks — tested · no policy violations · dry run passed · within budget — shown on the library card and above Run. Each links to its evidence. Editing the graph clears the marks, because a score that survives a change is a lie. Never show a numeric score; four booleans are honest, and a composite percentage invites the false confidence the score was meant to prevent.

LWorkspace ↔ Workflow relationship

Four surfaces already model execution. Their boundaries must be stated, or they will collapse into each other.

SurfaceOwnsGraph semanticsTime
Workspace (Hub)Can — reachable capabilities on this machineHub-and-spoke, deliberately not wireableNow
WorkflowsShould — a designed sequence the user authoredAuthor-time DAG, freely wireableDesign time
MissionsWill — an AI-planned task graph under human checkpointsRun-time DAG, deterministic layout, never hand-editedPlan → execute
RunsDid — what actually happenedNo graph of its own; projects the workflow'sPast
The distinction in one sentence

Workspace shows what your machine can do. Workflows are what you decided should happen. Missions are what the AI planned to do. Runs are what happened. A user who holds those four sentences can navigate the whole product, and any feature that blurs two of them is a feature to reject.

The seams that need building

  • Capability reachability, on the node. A node whose capability requires a connected node that is missing renders dimmed with needs Playwright, and clicking it deep-links to the Workspace's Add Node flow. This is the single highest-value connection between the two screens and it currently does not exist.
  • Project scoping, stated in the header. The editor already shows "runs against · aura-hub" — good. Extend it: runs record their project, the Runs view filters by it, and cross-project execution is refused with an explanation, per the research's privacy-boundary requirement.
  • Network awareness on the node face. Each node declares whether it needs the network. Offline, network nodes dim and the run header offers queue until connected. A workflow with no network nodes earns an offline-capable mark on its library card — the differentiator made visible rather than asserted in a comparison table.
  • Workflows as a Workspace panel. The dockable panel registry (ops/panels.tsx) has 15 panel kinds and no workflow panel. A compact "active runs + pending approvals" panel belongs there, so a user working in the Workspace can watch automation without leaving.
  • Do not merge Missions and Workflows. They look similar and are not: a mission's DAG is generated by an AI planner and gated by four checkpoints; a workflow's DAG is authored and gated by policy. Merging them would collapse two different trust models into one, and the checkpoint model would lose. The correct relationship is that a mission may invoke a workflow as a task, and a workflow may create a mission as an action — they compose, they do not unify.

MDesign principles

Ten rules that decide the arguments this project will actually have. Each is falsifiable — you can point at a screen and say it was broken.

01
Legibility over magic. When making something understandable and making it look effortless conflict, choose understandable. A user who cannot explain what just happened will not run it again unattended — and unattended is the entire product.
02
The graph is the truth; every other view is a projection of it. Timeline, ledger and trace are lenses on the same run, never independent stories. If two views can disagree, one of them is wrong and the user has no way to know which.
03
Identity and state never share a channel. Family hue says what a node is; ring and border say how it is doing. This separation already exists in shared.ts and is the reason a running graph stays readable. Never introduce a colour that means both.
04
Permission is visible before it is needed. A user learns what a workflow may do when they adopt it, not when it asks. The envelope precedes the gate; if the first time someone hears about process.execute is a modal at 2am, the design has failed regardless of how good the modal is.
05
Untrusted data always looks untrusted. Anything from a file, a page or an API is rendered as quarantined data wherever it appears. This is a security control that happens to be made of CSS.
06
Never hide non-determinism. Runs with an agent are marked as reasoned. Divergence between runs is inspectable, not surprising. Show what was measured; never show a confidence the model asserted about itself.
07
Calm by default, loud on risk. AURA's ambient motion — aura-breathe, aura-live, edge-flow — carries normal operation. Attention and danger tones are spent only on things that genuinely need a human. A UI that is always urgent has no way to signal urgency.
08
One authority per concept, in the UI as in the code. One timeline component, one approval component, one risk vocabulary, one node card, one DAG layout. CLAUDE.md's non-duplication rule is a UX rule before it is an architecture rule, because duplicated components drift and drifted components lie.
09
Failure is a designed path. Every node has a failure route, every wait states its cause and its exit, every denial offers a next step, every cancellation says what was and was not undone. Error states get the same design attention as success states — they are seen more often.
10
Every run is replayable, and replay uses the same components. History is not a downgraded view. A run from last week renders in the same instrument as the one happening now, so the skill of reading a run transfers completely between live and past.

NRecommended implementation order

Ordered by unlocked surface area per unit of work, not by the research's engine roadmap. Several high-value UX wins need no engine change at all.

Phase 0

Editor breathing room

Pure frontend. No backend dependency. Roughly a week, and it makes every later phase possible by returning the panel budget.

  • Palette search + collapse to icon rail
  • AI Builder becomes a summonable command surface instead of a permanent column
  • Inspector opens on selection; empty state becomes an overlay card
  • Validation strip with the three tiers (structure and config only — no policy yet)
  • Minimap; drag-from-palette-to-point; drop-on-edge splice
Phase 1

Runs exist

The highest-leverage change in the entire plan. Persisting runs unlocks six of the eight debugging affordances, the whole Runs surface, versioning's usefulness, and any notion of history.

  • Run persistence (id, version, trigger, steps, IO, logs, artifacts, outcome)
  • Global Runs table + run detail with graph / timeline / ledger
  • Shared selection across the three projections
  • Cancelled is distinguished from failed
  • Run summary lands on the library card ("last run 14h ago · ok")
Phase 2

Authority becomes visible

Turns AURA's real differentiator from an architecture fact into a product feature. Mostly a computation over the existing manifest plus one new view.

  • Permission envelope, computed from nodes, rendered in all six moments
  • Blocking review on import and on AI generation
  • Policy tier added to the validation strip; denials explain and offer a route
  • Secret references by name; visible redaction marks
  • Trust marks on the library card, cleared by edits
Phase 3

Humans in the loop

Depends on the engine's ability to pause and resume. The component already exists — this is placement and plumbing.

  • ApprovalGate inline in the run ledger; node enters waiting
  • Approvals inbox, risk-tiered and batched; StatusBar and bell integration
  • Scoped, expiring standing grants — listed and revocable
  • Clarification, credential and review-gate patterns
  • Timeouts park the run; they never auto-approve
Phase 4

Simulate and version

Together, because a version you cannot test is a version you cannot trust, and a simulation you cannot pin to a version tells you nothing.

  • Simulate view with blueprint canvas treatment and the prediction report
  • Mock configuration per node; policy and cost prediction
  • Versions view, graph diff, restore-as-new-version
  • Run promotes draft → version; version rows link to their runs
  • Envelope diff when a version widens authority
Phase 5

The Agentic AI Node

Deliberately last among the core phases. It needs the ledger (Phase 1), the envelope (Phase 2) and the inline gate (Phase 3) to be legible at all. Shipping it earlier produces exactly the spinner-and-JSON product this report exists to prevent.

  • Agent node face: indigo family, contract strip, three ports, beat ticker, iteration rail
  • Agent inspector: task + schema, context with token cost and freshness, tools as envelope, limits with worst-case estimate, on-failure route
  • Agent trace: typed rows, quarantined observations, always-shown permission rows, evidence-linked decisions, depleting budget meters
  • Inline intervention; terminal row names the limit that stopped it
  • Replay renders in the same component
Phase 6

Scale, recovery and reach

Everything that only matters once people have real workflows they depend on.

  • Step execution, breakpoints, run-from-here, run diff
  • Subworkflows (⌘G), auto-layout, node search
  • Data mapping: reference chips with provenance, edge peek, unresolved-reference validation
  • Rules and schedules join the Automations catalogue — the Automation Engine finally gets a face
  • Browser and desktop node families (--cat-surface-auto), CAPTCHA hand-off, live screenshot in the ledger
What this ordering buys

Phases 0–2 require no engine work beyond persistence and deliver: a usable editor at scale, a complete history, and visible authority. Phases 3–5 track the engine's own roadmap (pause/resume → checkpointing → agent loop) but arrive into a UI that can already explain a run. The dependency that actually matters is that the agent node must not ship before the trace surface it needs.

Summary

What is already right
  • The token layer, the two-channel colour model (identity vs state), and the ambient motion vocabulary
  • ApprovalGate's five required facts — the correct standard, already built
  • MissionTimeline's typed events and actor badges — reuse, don't fork
  • The canvas gesture grammar and the undo model
  • The Capability Fabric as one governed path — the genuine differentiator
What must change
  • Runs must persist — this unlocks most of the product
  • Authority must be visible before it is exercised
  • The editor must return its panel budget to the canvas
  • The Automation Engine needs a face
  • The agent node needs a contract and a ledger — and must not ship before the ledger exists
The one-line test for every screen in this plan

Show it to someone whose machine just ran an agent unattended overnight. If they cannot answer what did it do, what was it allowed to do, and why did it decide that — without opening a log file — the screen is not finished.
